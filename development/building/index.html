    Building¶

    cmake -B build .
cmake --build build

    Dependencies and the per-platform install rules are in Installing. This page is what a contributor needs beyond that.

    Qt 6.2 is the floor, and the Qt 5 fallback is gone¶

    For most of this project's life the root configuration looked for Qt 6, fell back to Qt 5, and set a version variable so that every link line and two conditional blocks could follow. Six QML files carried a sentence explaining what the Qt 5 path would cost them.

    All of it is gone, and the argument is not that Qt 5 is old:

    Nothing verified it, and one thing made it unverifiable. No build of this project has ever been made with Qt 5 — not on either desk, not in either CI job — and it could not have been: eleven of the QML suites call waitForPolish, which arrived in Qt 6.5, so a Qt 5 configure would have produced a build whose own test suite could not run.

    A fallback that no run exercises is not a fallback; it is a set of conditionals that read as safety while guaranteeing nothing. Same fault as a find_program guard that skips in silence.

    The floor is 6.2 rather than 6.5, and that gap is deliberate. 6.2 is the oldest Qt 6 LTS and what a long-term distribution ships; the app builds and runs against it. What needs 6.5 is the test suite, which a packager does not run — so raising the floor to 6.5 would refuse to configure on a machine where the product itself works.

    Three uses in the QML tree are genuinely version-guarded — the system colour scheme (6.5) and the two native choosers (6.3) — and those guards stay: an unsatisfiable import is fatal to the whole file that writes it, which is why the two choosers sit behind loaders.

    Warnings¶

    -Wall -Wextra (/W4 on MSVC) are on and -Werror deliberately is not.

    The compiler's default is close to silent, which is how a /* inside a block comment reached a reader rather than whoever wrote it. Turning the warnings on is one decision; failing the build on them is a second one with a different cost — a toolchain upgrade adds diagnostics, and a build that stops on those is a build that gets the flag removed rather than the code fixed.

    They are set once at the root, so the library, the app and every test executable are held to the same standard.

    A glob in a block comment

    The prose in this codebase is long and quotes patterns, and vendor/** or /sub/*.log inside a /* … */ block opens a nested comment as far as the compiler is concerned — and everything to the next */ is then being read as one comment. Write the prefix and the wildcard as separate quoted pieces, or use // blocks.

    MSVC needs four flags, and three of them are not preferences¶

    • /utf-8 — MSVC reads source in the machine's ANSI code page, and this tree's comments and labels carry ⌘, ⏎ and ⇧. Without it those are the first thing silently wrong.
    • /permissive- — MSVC's pre-standard lookup accepts templates the other two compilers refuse, which is how a third platform becomes a fork.
    • /bigobj — raises an object file's section limit. It is here rather than after the first failure because that failure is a hard error, not a warning.
    • /W4, and no /WX, for the reason above.

    The precompiled header¶

    The 129 translation units are half of CI's wall clock, and a precompiled header takes a fifth off it. Measured against a cold build with no compiler cache, at --parallel 2 with four other builds running:

    wall user (CPU) sys
    before 2m45.9s 4m36.2s 49.4s
    after 2m12.5s 3m25.5s 53.2s
    −20.1% −25.6% +7.7%

    The CPU figure is the one to believe — wall clock on a machine running four other builds is a measurement of the other four as much as of this one. The sys column going up is the honest cost and is what it should be: a ~100 MB file read once per object instead of parsing headers.

    Sixteen Qt headers and nothing of this project's own, chosen by how many units include them rather than by taste. Nothing local, deliberately — a precompiled header holding the god header would make an edit to it rebuild every object in the library, which is the cost this is supposed to remove, paid on the edit somebody is actually making.

    One for the library and one for the suite. The library's is private: a public one is inherited by everything that links the target, which would put a second, differently-flagged compile under each of the sixty test executables.

    The god header cannot be split, and that was checked rather than assumed. The manager includes all 51 controller headers and 44 of the library's 83 units include it, so editing any controller header rebuilds over half the library. The obvious fix — forward-declare the controllers, move the includes into the source — does not work: moc requires the complete type for a property of pointer type, and the generated unit sees only the header. Demonstrated on a three-line file rather than argued from memory.

    What is left after the precompiled header is not includes. With nine more headers added, chosen the same way, a cold library build went from 1m07.8s to 1m05.0s — 4%. That is the headroom include hygiene has here; what remains is template instantiation across 83 units.

    A unity build was not done, and would not be

    It is the larger win and it changes what the compiler sees: concatenated units share a translation unit, so a missing #include in one file is supplied by whichever file happened to be concatenated above it — and the build stays green until somebody reorders the list or compiles that file alone.

    A precompiled header cannot do that, since it is a prefix every unit gets whether or not it asked. That asymmetry is the whole reason one of these is here and the other is not.

    Presets¶

    CMakePresets.json holds the build configurations — debug / release, each with an -install variant — and is committed because Qt Creator's own build configuration is not: that lives in a gitignored file, is rewritten by the IDE, and carries a kit UUID from the developer's own profile. A preset is the only way for the repository to say how the project is built.

    The one thing a committed preset cannot supply is where Qt lives, which is machine-specific. See Installing for the gitignored user-preset that pins it robustly.

    Packaging: two targets, and the scripts under them¶

    cmake --build build --target dmg   # macOS: a drag-to-install disk image
cmake --build build --target deb   # Linux: a Debian package

    Each is declared only on the platform that can run it — a deb target on macOS would be a target that fails when pressed — and neither is in all: packaging takes minutes and is something a person asks for.

    Both are a front door and not an implementation. The work is tools/make-deb.sh and tools/make-dmg.sh, and it is there for two reasons: the release pipeline runs them without a build tree of the shape a CMake target needs, and a shell script can be tested — test_debpackage and test_dmgimage run these directly, and ci.yml runs both for real on every push. A target that inlined the steps would be a second implementation, exercised only by whoever happened to use it.

    What each produces, and what it deliberately is not, is in Releasing.

    The disk image, on a Mac¶

    --target dmg stages the built bundle, runs macdeployqt over it to copy Qt in, ad-hoc signs it — not optional on Apple Silicon, where the kernel refuses to run code whose signature does not match its contents — checks with tools/verify-macos-bundle.sh that nothing in it still points at your Homebrew prefix, and lays the window out: the app on the left, an Applications symlink on the right, an arrow between them. It prints the path it wrote.

    The window's layout is Finder's, driven by AppleScript, so the first run asks whether your terminal may control Finder. Refusing is not fatal: the image is still built, undecorated, and the script says loudly that it has no layout. That is also what happens on a CI runner, which has no GUI session — so the decoration is the one part of the image CI cannot check, and test_dmgimage's arithmetic plus opening a release candidate on a Mac is what covers it.

    It is not notarised. Whoever you send it to right-clicks > Open the first time. To sign it properly, pass a Developer ID Application identity:

    ./tools/make-dmg.sh --build-dir build --output build/packages \
  --sign "Developer ID Application: … (TEAMID)"

    The .deb, from a Mac, in a container¶

    --target deb needs dpkg-dev, so it exists only on a Debian-ish machine — on macOS the target is absent rather than failing when pressed. What builds one from a Mac is Docker, running the same script:

    docker run --rm --platform linux/amd64 -v "$PWD:/src" -w /src ubuntu:24.04 bash -c '
  apt-get update &&
  DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends \
    cmake ninja-build g++ pkg-config dpkg-dev \
    libgit2-dev libssl-dev libsecret-1-dev \
    qt6-base-dev qt6-declarative-dev qt6-tools-dev qt6-l10n-tools &&
  cmake -S /src -B /tmp/b -G Ninja -DCMAKE_BUILD_TYPE=Release &&
  cmake --build /tmp/b --target SourceManager &&
  /src/tools/make-deb.sh --build-dir /tmp/b --output /src/build/packages'

    --platform linux/amd64 is not optional on Apple Silicon

    A .deb is built for one architecture and dpkg refuses it on any other. Without the flag you get an arm64 package — right for a Raspberry Pi, useless to everybody on an ordinary PC. The cost is that the build runs under emulation and takes several times longer.

    Build it on the oldest distribution it should install on. The package depends on the Qt it was linked against, so one built on 26.04 will not install on 24.04 and one built on 24.04 installs on both; on a newer distribution dpkg-shlibdeps also picks up qt6-declarative-private-abi at an exact version, which pins the package to that Qt patch release. ubuntu:24.04 is the release pipeline's own choice for both reasons.

    It is also the floor the app has to compile against, and that is not a formality: Qt 6.4 in that container against 6.10 on a current desk found two APIs newer than the floor that had reached the tree and compiled everywhere else — beginFilterChange() in a proxy, and a closing connection needing a QQuickCloseEvent Qt keeps private before 6.6. A container run is one step short of a release; finding them there is the point of doing it.

    Install the result with apt, never dpkg -i — apt pulls the dependencies in, dpkg only reports that they are missing:

    sudo apt install ./build/packages/source-manager_*.deb

    How old a macOS the build runs on¶

    The cask says depends_on macos: ">= :sequoia", and that is a description of the artifact rather than a policy. The floor is the highest of three numbers, and only one of them is this project's:

    1. Your own deployment target. CMAKE_OSX_DEPLOYMENT_TARGET is not set anywhere here, so the binary is built for whatever SDK the build host has — macOS 15 on the macos-15 runner.
    2. The minimum of the Qt frameworks macdeployqt copies in. Homebrew builds its bottles per macOS version, so a brew install qt on Sequoia gives frameworks built for Sequoia. This is the number that usually decides it, and it is the one people miss: setting a deployment target on your code does nothing about the frameworks sitting next to it in the bundle.
    3. What Qt itself supports. Qt has been dropping macOS versions steadily; check the release notes for the version you are on.

    Read what a built bundle actually claims rather than trusting any of the above:

    otool -l build/packages/stage/SourceManager.app/Contents/MacOS/SourceManager | grep -A3 LC_BUILD_VERSION
otool -l …/Contents/Frameworks/QtCore.framework/Versions/A/QtCore | grep -A3 LC_BUILD_VERSION

    Lowering it¶

    Build the release on an older runner. Change runs-on: in the macOS job to the oldest image GitHub still offers (macos-14 at the time of writing — actions/runner-images is the list that is actually current), and Homebrew there installs bottles built for that OS. That is the whole change: one line, and the cask's depends_on macos: to match.

    Three costs, and none of them is large:

    • You can only reach as low as the oldest runner image, and those retire. Below that means building on hardware you own, where Homebrew supports only the last three macOS versions and will try to compile Qt from source on anything older.
    • An older image is an older toolchain. Not a problem for this code today, but it is one more compiler the tree has to keep compiling under, and CI would want the same pin or the two disagree.
    • It is a claim about an OS nobody tests on. This project is loud about not saying "Windows works" on the strength of a green headless job; the same applies here. Lower the floor and move the CI macOS job to the same image, or say the floor is where it is tested and no lower.

    Intel is a different question¶

    depends_on arch: :arm64 is not about the deployment target: Homebrew's Qt, libgit2 and OpenSSL are single-architecture, built for the machine they are installed on. Adding an x86_64 slice means dropping Homebrew as the dependency source — qt.io's own macOS packages are universal, but libgit2 and OpenSSL would then have to be built universal too, and verify-macos-bundle.sh exists precisely because that chain is where things quietly go wrong.

    It is a real piece of work rather than a flag, and worth doing only if somebody is actually on an Intel Mac.

    Cross-building: what is and is not possible¶

    From → to Possible? How
    macOS → Linux .deb yes Docker, above. Not really cross-building: a native Linux build inside a container, emulated for amd64 on Apple Silicon
    Apple Silicon → Intel macOS in principle -DCMAKE_OSX_ARCHITECTURES=x86_64, but every dependency needs an x86_64 slice and Homebrew's have none — see above
    Linux → macOS no The SDK cannot be redistributed, codesign and hdiutil are macOS-only, and macdeployqt runs nowhere else. osxcross exists and none of the packaging does
    anything → Windows no MSVC, and the pipeline is the only place this project has ever built for Windows
    Linux → other Linux yes The same container trick with a different base image

    The short version: macOS builds happen on a Mac and Windows builds happen in CI. Everything else you can do from either.

    Translations are compiled every build, and extraction is not¶

    The .ts catalogues are source: they carry human translations and a per-message "unfinished" flag a translator clears by hand, so a build that reran extraction would make every compile a working-tree modification and would race two build directories against one file.

    cmake --build build --target update_translations

    Location comments are switched off, because file-and-line comments move every message in the file whenever a line is inserted above it, and document where a string was rather than anything a translator needs.

    Linguist is required, and refusing to configure without it is the icon's lesson applied. The app icon was once assembled behind a guard that skipped in silence, and what it produced was a bundle with no icon and a status line nobody reads. A missing lrelease is the same failure with a worse face — the build succeeds, every test passes, and the app speaks one language for reasons no message anywhere explains.

    The icon¶

    One generator draws the mark and writes four readings of it: the .iconset of PNGs, the macOS .icns, the Windows .ico, and — from the same PNGs — the six sizes the Linux install rules file into the icon theme.

    Both the .icns and the .ico are committed. The first version assembled the .icns at build time with a macOS-only tool wrapped in a guard that skipped in silence, so any build without it produced a bundle with no icon. Writing the container in the generator makes the icon a build input like any other file.

    The window icon is a separate thing and is set from the resource: the .icns is what Finder and the Dock show for the application, while the window icon is what a running window carries in the switcher and on every platform with no bundle at all. Setting one and not the other is how an app ends up with an icon everywhere except where you were looking.

    Three details differ per platform and each is a reason rather than a taste: the .ico is compiled into the executable, because that is where Explorer reads one from; it has a 48 where the .iconset does not, because Windows picks an entry out of one file while an icon theme scales the nearest size it holds; and its resource id is a bare 1, because the shell shows the lowest-numbered icon resource.

    Diagnostics¶

    Two command-line flags, off by default, and both draw into the window as well as printing:

    • --trace-timing — every controller refresh, the whole of opening a repository, each navigation, each surface built. They nest, and the lines are indented by depth.
    • --trace-swipe — a line per wheel event with its phase, both deltas, the accumulated travel and whether anything moved.

    The panel is not belt and braces. A line on stdout is invisible to an app launched from Finder, can be filtered by a logging rule, and is absent altogether when the build predates the change — and all three read as "the trace does not work", which is indistinguishable from "the thing being traced never happened", which is the question. The panel appears the moment the flag is honoured, so the first is settled before the second is asked.

    A flag rather than a setting, because it is a diagnostic somebody runs once rather than a choice about how the app behaves. Off, every entry point returns on a bool and allocates nothing, which is what lets the calls sit in the hot paths — and the switch is writable, so a test can turn it on: the swipe trace shipped switched off on every platform the suite runs on and nothing noticed, because its switch was a platform check no test could reach.

    A release build compiles them out entirely.
